## Findings

### 1. The theme record has not run since v436 (bars 83-92; process)

**Problem.** `python3 symphony/coherence/themecheck.py symphony/coherence/themes-mvt2.ly symphony/mvt2/vNN` reports 18/18 on v434 and v435 and crashes on v436 to v440 with `ValueError: max() iterable argument is empty` (lyparse.py line 141). The cause is c435's `<>\strMark "L" ...` at the start of codaVla (coda.ily line 35). lyparse reads `<>` as a chord with no pitches. So the record that guards the link from movement I, the motto tails, the quotations and the last chord (the "nothing is locked, but report changes" rule in BRIEF) has not been checked for five versions. Records listed in HISTORY after c430 do not say 18/18, and kit/accept.sh runs only guard.py, not themecheck.py.

**Evidence from the reading.** Rimsky's preface treats the colours of an idea as part of the idea (PDF 20). Quoting movement I at its own pitch and colour (rows 1, 9, 16) only works if each version is checked against the other movements. The editor (PDF 18) lists faults that came from details nobody checked.

**Fix (tested).** Patch the shared lyparse.py so an empty chord counts as zero length. The same patch also stops a tie inside a chord from hiding that chord's note (`<fes aes~>` was read as F♭ alone):

```
-            ps = [pitch(x) for x in m.group(1).split() if pitch(x) is not None]
+            ps = [pitch(x.rstrip('~')) for x in m.group(1).split() if pitch(x.rstrip('~')) is not None]
+            if not ps:  # '<>' is an empty chord of zero length, not a note
+                continue
```

The patched copy is in /tmp/critic-440/tools/ (diff: lyparse-c440.patch). On v440 it gives 18/18 and 11/11. The scherzo record still gives 52/52 against scherzo v400, so the patch changes nothing for the other movements. The finale thread merges lyparse changes, so send it the patch. Also add the check to kit/accept.sh after guard.py:
`python3 $M/../coherence/themecheck.py $M/../coherence/themes-mvt2.ly $M/v$NEW > /tmp/tc.txt || echo "THEME RECORD CHANGED"; tail -1 /tmp/tc.txt` and the same for themes-mvt2-b.ly with `--beats 4`. themecheck.py exits with 1 when an entry changes, so every promotion then prints either "theme record: 18/18 unchanged" or a warning.

If the parser cannot be changed now, use the score-side fix. I applied it in /tmp/critic-440/work, coda.ily line 35: `<>\strMark "L"` → `s2.*0\strMark "L"`. With it the unpatched themecheck reads 18/18. The build is clean (0 warnings), score.midi is byte-identical to v440, all 8 score pages are pixel-identical at 60 dpi, and the parts book is 30 pages, pixel-identical to v440's.

### 2. The record does not cover the violas' coda line, which the finale quotes (84-89)

**Problem.** In v436-v439 the violas' bars 84-85 were lost inside a comment, so the violas entered two bars early. That moved the F3-F♭3-E♭3 mixture line, and the violas were missing from the last chord at 91-92 (c439 found and fixed it). Even with a working parser the record would not have caught this: `mixtureLineLow` is checked only in Horn 4, and no entry reads the violas after bar 2. The finale quotes this line "in the violas and Hn 2 ... at the same pitch" (finale.md items 11, 28, IV 197.4-198), so it is a cyclic export.

**Evidence from the reading.** PDF 128-129: the coda's F-F♭-E♭ is the muted, octave-lower echo of Hn 3 and the violas at 79-81. The violas are the string half of that echo, so the line should be checked in the violas as well as the horn.

**Fix (tested).** Add to themes-mvt2.ly:

```
% codaVla: violas 84 b3-87, top note of each divided chord (lyparse reads a chord's highest pitch); the finale quotes 87-89 (IV 197-198)
codaVla = { r2 es'4~ | es'2. | f'2. | aes2. }
%@ codaVla Vla 84
```

Tested with the patched parser (/tmp/critic-440/tools/themes-mvt2-c440.ly): 19/19 on v435 and v440, and "CHANGED codaVla" on v436, v438 and v439. It catches the regression.
